# compliance-mapping — shared mechanism behind every *-compliance-check agent

Read `../folder-scan/SKILL.md`, `../term-sweep/SKILL.md`, and `../report-export/SKILL.md` first, plus `../sharing-exposure/SKILL.md` in every plugin that bundles it (every Signal-B framework does; section-508 and wcag run Signal D only and do not). This skill adds nothing new at the connector-call level — it orchestrates those files exactly as `sensitive-content-scanner`, `sharing-auditor`, and `retention-sweeper` already do, under one gap-report shape reused across every regulatory framework.

## Say this before anything else — the honesty framing this whole family depends on

**A Kiteworks folder scan can only ever see three things: what's in file content, whether a file sits in a shared folder tree (sharing is a folder property; files inherit it), and how old a file is.** That's it. It cannot see network architecture, encryption implementation, cloud configuration, contractual clauses, incident-response procedures, board governance, export licensing status, or almost anything else a real compliance program actually consists of. Every `*-compliance-check` agent in this family exists to surface the narrow slice of a named framework that maps to those three signals — nothing more — and every one of them must say so plainly, every time, not just in fine print. Never let a report read as "compliant" or "certified" for any framework; the only honest claim this mechanism can ever make is "no [signal] issues found in what we scanned," which is categorically different.

## The three signals, and how each is actually checked

**Signal A — sensitive-content exposure.** Reuses `term-sweep`'s content deep-scan and built-in PII/secret pattern presets (`scripts/pii_patterns.py`) exactly as `sensitive-content-scanner` does, plus whichever framework-specific term list this framework's own skill supplies (see "Framework-specific term lists" below). Content term hits are counted only by `pii_patterns.py <extracted-text-file> --framework=<slug> --framework-terms`, plus `--terms-file=<user-terms.txt>` for the user's own terms, per term-sweep's "Counting terms in extracted text" -- never by the agent itself, so the same file gives the same counts on every run. Opt-in, same as `term-sweep` — tell the user the candidate count before running it.

**Signal B — sharing exposure (effective).** The mechanism is `../sharing-exposure/SKILL.md`, the same one `sharing-auditor` ships: read the scan root's own `isShared` flag first; if it is shared, resolve the share origin above it (one call per level, once per scan); then walk with `get_folder_children` and report one finding per share origin with the counts of files and subfolders that inherit, because the flag cascades and files never carry it. The boolean cannot say *who* has access or whether they are internal or external: say "sharing exposure", never "external sharing". No separate implementation — the same check, reported under this framework's lens.

**Signal C — policy-age review candidates.** Compare available file timestamps with an applicable documented policy or review cadence, recording the reference field and its limitations. A file timestamp is not proof of business purpose, last review, last effectiveness or a legal violation.

Classify each cited obligation before using a number:

1. **No applicable age-based check:** omit C and explain what is not assessed. Do not invent a policy or a citation.
2. **Purpose/policy-based retention:** ask for the organization's applicable policy, duration and reference event; record the answer and any missing context. GDPR storage limitation does not prescribe a universal number of years. A configured cutoff produces review candidates, not disposal instructions.
3. **Periodic review:** a stated cadence can prioritize candidates, but a confirmed overdue finding needs the actual last-review event. If only creation/modification is available, identify it as a proxy and say review history is unknown. DORA uses this category.
4. **Minimum retention:** do not implement it by flagging files that are old. HIPAA's six-year Security Rule documentation obligation (45 CFR 164.316(b)(2)(i)), ITAR/EAR minimum recordkeeping and PCI audit-log retention are minimums, not maximum ages. A folder scan cannot establish that deleted records were retained long enough. HIPAA Signal C does not run on file age.

Never substitute `modified` for last-effective date or last-review date. Record legal holds, business purpose and policy applicability as unknown when unavailable. Validate the specific document type and obligation before drawing a conclusion. Sources: HIPAA [HHS Security Rule summary](https://www.hhs.gov/hipaa/for-professionals/security/laws-regulations/index.html); framework-specific primary citations in each profile.

**Signal D — accessibility structure (two frameworks only: `section-508-compliance-check`, `wcag-compliance-check`). Operational as of 2026-07-14 — real tooling, not a description of a check that doesn't run.** Not about PII/sharing/retention but about whether documents in scope are usable by assistive technology. Runs `scripts/accessibility_check.py` (bundled with this skill; DOCX, PPTX and HTML need only the Python standard library, and PDF needs `pikepdf` through the one supported command below) against each PDF/DOCX/PPTX/HTML pulled locally via `content-extract`'s binary-bridge path. For PDF and DOCX this genuinely checks and reports: whether the PDF is tagged (`MarkInfo.Marked` + a real `StructTreeRoot`, not a guess), whether document-level language metadata is set, whether Title metadata is set, and how many figures carry `/Alt` text (PDF) or a `descr`/`title` attribute (DOCX) versus how many don't. For PPTX it additionally checks per-slide title-placeholder text (`slides_total`/`slides_with_title`) and picture-shape `descr`/`title` attributes walked recursively into group shapes — note the caveat baked into the script itself: python-pptx's own `add_picture()` auto-populates `descr` with the source image filename by default, so a non-empty `descr` on a python-pptx-generated deck means the attribute is present, not that it's meaningful authored alt text; same "presence not quality" limitation as the PDF/DOCX checks. For HTML/HTM it checks `<html lang>`, a non-empty `<title>`, whether headings skip a level (e.g. h1 straight to h3), whether an `<h1>` is present, and `<img alt>` presence — no browser or rendering engine, so JavaScript-injected content is invisible to it. Only `.pdf`, `.docx`, `.pptx`, `.html`, and `.htm` are supported; any other file type in scope is reported as explicitly skipped, never silently ignored.

This is still a structural heuristic, not a full WCAG or PDF/UA conformance test — real conformance testing needs interactive tools (screen reader and keyboard-navigation testing) and human review, which this cannot replace. Say so explicitly every time, and never claim a document "passes" or "fails" a conformance level — only "no obvious structural issue found in this check" or the specific issue the script reported (e.g. "not tagged," "3 of 5 figures missing alt text," "heading level skipped h1 -> h3"). Before 2026-07-14 this signal was described but had no working implementation behind it (`content-extract` is a text extractor: `pdftotext` for PDF and its own standard-library reader for DOCX, PPTX and XLSX, none of which can see tag structure) — `section-508-compliance-check` and `wcag-compliance-check` should now be treated as **Operational** rather than **Not yet operational** in any report or documentation that states operational status (see the badge convention below). PPTX/HTML coverage was added the same day as a follow-up pass. Since #293 the script reads DOCX and PPTX with its own standard-library zip/XML reader (the approach `content-extract` uses), so PDF is the only format that needs a third-party package.

**Running Signal D — one supported install path, no ad-hoc environments (#293).** Run DOCX, PPTX and HTML files with any Python 3: `python scripts/accessibility_check.py <file>`. Run PDF files with the pinned command `uv run --with pikepdf==10.13.0.post1 python scripts/accessibility_check.py <file>`; uv resolves pikepdf into its own cache outside the run folder, so nothing is left behind and every run uses the same version. When pikepdf is missing (no uv, or plain `python` used for a PDF), the script does not crash: it prints a JSON result whose `error` names the missing package and the command above, sets `"missing_dependency": "pikepdf"`, and exits with status 2. Report each such PDF in the Scope section as "not checked: pikepdf unavailable" — never as passing, never silently dropped. **Never build your own virtual environment, and never `pip install`, in the run folder or the scratch directory.** If you had to create any environment anyway, delete it before the run ends and say so in the Scope section.

## Signal E — cross-border transfer (dormant, capability-gated)

Several frameworks in this family (GDPR, LGPD, DPDPA, VN-PDPL, ITAR, EAR) care specifically about *where* content ends up or *who* a recipient is, not just whether it's shared. Kiteworks' connector does not currently expose a recipient country/region field on any share or file record — only `isShared` (boolean). Rather than skip this permanently or fake it, each framework skill that lists Signal E treats it as **dormant**: probed for at runtime, not hard-coded as present or absent.

**Location evidence requires verified field semantics.** Candidate fields may include `region`, `residency`, `dataResidency`, `country`, `recipientCountry`, and `shareRegion`. Their presence alone never activates a cross-border finding. Keep Signal E dormant unless the connector capability contract establishes the meaning, object type and provenance of a field and the relevant source/destination context. Storage residency, recipient location and nationality are different facts. A generic `dataResidency=EU` must never become a claim that a recipient is in the EU or that a transfer occurred.

When verified location evidence is available, record precisely what it establishes. Unknown/null values remain unknown. Jurisdiction, authorization, legal safeguards and export classification require separate evidence and review; do not infer them from a country string. Report missing location evidence once in the executive coverage limits and in the appendix's check statuses.

## Framework-specific term lists — an intentional, justified exception to term-sweep's default rule

`term-sweep`'s general rule is "never invent a term list without asking — sensitivity vocabulary is organization-specific." That rule is about *organization-specific* vocabulary (client names, internal project codenames) where there's no correct default. Regulatory frameworks are different: HIPAA's vocabulary for protected health information, ITAR's vocabulary for controlled technical data, CMMC's vocabulary for CUI markings are not organization-specific — they're defined by the framework itself, the same way "SSN-shaped" and "IBAN-shaped" are defined by the built-in PII presets, not invented per-org. So each `*-compliance-check` skill that uses Signal A supplies its own sensible default term list (documented in that skill's own file, sourced from the public framework documentation, cited), and still lets the user add their own on top — the same two-layer pattern `term-sweep` already uses for built-in presets plus custom regex. Each list is also built into `term-sweep/scripts/pii_patterns.py` as `FRAMEWORK_TERMS`, which `--framework-terms` counts; `tests/test_pii_patterns.py` asserts the two are identical, so change a list in both places together.

## What every framework's own skill must supply

A `*-compliance-check` skill is thin by design — it should never reimplement any of the mechanism above. It supplies only:

1. **Tool suitability** — internal capability documentation only. Strong/Good/Light/Accessibility/Minimal are not organization compliance ratings and must not be used as executive-result badges. HIPAA uses A/B; other privacy profiles may use A/B/C with a supplied policy.
2. **Which checks apply** — applicable internal A/B/C/D/E identifiers, deterministic term lists, actual methods, policy/criterion provenance, and why each other check is not applicable or not attempted. Use the obligation categories above for age-based checks.
3. **An explicit "what this doesn't check" paragraph** naming the real bulk of that framework's requirements that this mechanism has no visibility into at all (drawn from the framework's actual scope, not a generic disclaimer) — for a *Minimal*-tier framework this paragraph is most of the skill.
4. **A "Control citations" section, where real primary-source citations exist.** This is the actual regulatory article/section/control number each signal maps to, drawn from the primary legal or standards text (official government publication, EUR-Lex, eCFR, the standards body itself) — never from the third-party GRC skill library's own descriptive text, which is copyrighted third-party material this mechanism paraphrases but never lifts verbatim. Where a citation could not be independently verified against a primary source during this project's research (this happens — some regulatory texts aren't freely mirrored, and ISO standards are sold, not published), say so plainly instead of inventing a plausible-looking article number. A missing citation is an honest "not verified," never a guess.
5. **A citation back to the source** it was adapted from — the 30-skill GRC library at `sushegaad/Claude-Skills-Governance-Risk-and-Compliance` (each framework's own page there, linked) — for anyone who wants the actual depth (SSP drafting, licensing walkthroughs, breach-notification procedures, etc.) that this productivity-scan mechanism deliberately does not attempt. This citation is to the library's existence and structure, not a reproduction of its text.
6. **A "Recommended next steps" paragraph** — concrete, framework-specific actions the organization should take *beyond this scan* to actually assess this framework (e.g. "complete a formal DPIA," "engage a licensed CPA firm for the Type I/II audit," "commission real assistive-technology testing"), not generic advice. This is required content, not optional — it renders into every report's dedicated "Recommended Next Steps" section (see below) and is the single most load-bearing piece of the honesty framing, because it's what turns "here's a narrow gap in what we could see" into actionable guidance rather than a dead end.
7. **Tool availability** — record limitations in methodology. Distinguish this from the actual run coverage derived from its ledger; an operational tool does not mean a complete assessment.

## The report

Depending on the configured checks, coverage may include content exposure, sharing exposure, and retention age; a framework may omit these checks or run document-structure checks instead. Record only checks actually performed.

Use `../report-export/SKILL.md` and the version-2 assessment contract in `../kw-pdf-report/SKILL.md`. Select the framework's profile from `../kw-pdf-report/report-profiles.md`. Fill the record in new mode: include `report_mode`, `cover` and a `kind` (`content` or `metadata`) on every check, and use the canonical priorities `critical`, `high`, `medium`, `low`, `info`. Map the tool's fit-tier language to priority, never to severity; a fit tier is not a severity. Write one finding per business theme, never one per file, with `example_object_ids` for up to three examples. Generate PDF, complete inventory CSV and narrative TXT from the same assessment record, only in the formats/destination already authorized.

The executive summary starts with purpose, a bounded conclusion, principal observations, implications and decisions. Do not put internal Signal A/B/C/D/E labels or Strong/Operational badges on the executive pages. Use plain-language topics such as possible personal data, access arrangements requiring review, policy-age candidates and document accessibility barriers. Retain check identifiers in methodology and the per-object inventory.

The main body groups significant findings by business theme. Each finding needs observation, why it matters, evidence confidence, priority rationale, relevant object/check IDs, a cited criterion when verified, and a concrete recommended response. Proposed owner roles and target dates are not accepted commitments. Include material coverage limits beside the conclusion, not just in fine print.

Every enumerated file appears in the ledger, including no-hit, skipped, failed and metadata-only items. Record the status of every configured check for every object. Include OCR method and unreadable reasons without printing matched personal data or secrets. Preserve sharing-context, share-origin and membership visibility per `sharing-exposure`; a shared folder does not establish external or unauthorized sharing. Detailed per-file OCR/skips belong in the appendix, while aggregate coverage and unvisited scope remain prominent in the summary.

Include the full framework-specific limitations and next-evidence requests from the profile. Do not invent control citations, risk scores, affected-person counts or legal conclusions. A no-finding result means only that the completed checks detected no issue. Set `report_mode.inventory` to `companion` when CSV and PDF are both authorized (same report ID/version), `compact` for PDF-only, and `omitted_by_request` only on explicit request. Never silently truncate or add an unrequested export.

Preserve the published legal footer and plugin scope caveat. This is a content-governance screening report, not certification, an audit opinion or a legal determination of compliance. It does not assess organizational controls beyond the recorded evidence.

When extraction reports `not content-checked: OCR unavailable (tesseract not found)`, preserve that exact reason in the inventory and classify the content check as skipped. Never relabel it as a clean result.
